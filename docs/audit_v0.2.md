# AdaptiveSense v0.2 — Audit of v0.1

Purpose: record, **before any code change**, every correctness / research-validity
defect found in the v0.1 tree (`commit ab5c86a`). Each entry was confirmed by
reading the actual source, not by assuming a reported symptom is still present.

The section *Verification of the fixes* at the end of this document maps every
entry to the evidence that it is actually gone.

Severity scale:

| level | meaning |
|-------|---------|
| **P0** | affects correctness, or the code cannot run/build at all |
| **P1** | seriously undermines experiment validity |
| **P2** | engineering-quality issue |

Legend for **Status**: `Confirmed` = reproduced by reading the code; `Verified`
= additionally reproduced by executing code (test / build / script output).

## Detail

### 1 — P0 — BME280 humidity calibration is read out of bounds and from the wrong registers

* **File**: `firmware/main/sensor.c:98-123`
* **Root cause**

  ```c
  uint8_t buf[26];
  bme_read(0x88, buf, 26);            /* 0x88..0xA1 -> dig_H1 lives at buf[25] */
  ...
  bme_read(0xE1, buf, 7);             /* only buf[0..6] valid                   */
  bme_cal.dig_H1 = buf[0];            /* WRONG: this is 0xE1 = dig_H2 LSB      */
  bme_cal.dig_H2 = buf[1] | buf[2]<<8;/* WRONG: shifted by one                */
  bme_cal.dig_H3 = buf[3];            /* WRONG: 0xE3 is buf[2]                 */
  bme_cal.dig_H4 = (buf[4]<<4)|(buf[5]&0x0F); /* WRONG: 0xE4 is buf[3]        */
  bme_cal.dig_H5 = (buf[6]<<4)|(buf[5]>>4);   /* WRONG: 0xE5 is buf[4]        */
  bme_cal.dig_H6 = (int8_t)buf[7];    /* OUT OF BOUNDS: buf has 7 valid bytes  */
  (void)buf[8];                       /* OUT OF BOUNDS: reads uninitialised    */
  ```

  Per BME280 datasheet (BST-BME280-DS002) Table 16, memory map:

  | address | field |
  |---------|-------|
  | `0xA1` | `dig_H1` (u8) |
  | `0xE1`/`0xE2` | `dig_H2` (s16, LSB first) |
  | `0xE3` | `dig_H3` (u8) |
  | `0xE4`, `0xE5[3:0]` | `dig_H4` (s12) |
  | `0xE5[7:4]`, `0xE6` | `dig_H5` (s12) |
  | `0xE7` | `dig_H6` (s8) |

  Consequences: `buf[7]`/`buf[8]` are undefined reads (only 7 bytes were
  written), the whole humidity calibration block is shifted by one register, and
  `dig_H1` is taken from the wrong block entirely. Humidity would be wrong even
  though the compensation equation itself is correct.
* **Fix**: read `dig_H1` from `buf[25]` of the 26-byte block at `0x88` (exactly
  what Bosch's own reference driver does), read 7 bytes at `0xE1`, use the
  datasheet indices `[0..6]`, and sign-extend the 12-bit `dig_H4`/`dig_H5`.
  Check every `bme_read()` return value.
* **Validation**: host-side unit test that feeds a synthetic register image of
  the 26-byte and 7-byte blocks and asserts the parsed constants, plus an
  address-sanitizer-style bounds review; a compile-time `static_assert` on the
  buffer size.

### 1b — P0 — the humidity Q-format conversion is off by a factor of 4096

* **File**: `firmware/main/sensor.c:158-170, 236-239`
* **Root cause**: the datasheet-appendix integer humidity routine leaves the
  result in a 22-fractional-bit accumulator (`x1 ≈ %RH × 2^22`, which is why its
  own guard clamps at `419430400 = 100 %RH × 2^22`). The official driver then
  reduces it with `>> 12` and divides the Q22.10 result by `1024`. v0.1 skipped
  the `>> 12` step and divided the raw accumulator by `1024` only.
* **Evidence**: the two implementations were compared numerically on the same
  synthetic calibration constants and raw register value
  (`adc_H = 26559`, `adc_T = 534203`):

  | conversion | result |
  |------------|--------|
  | Bosch double-precision reference | **44.998 %RH** |
  | `(x1 >> 12) / 1024` (official integer form) | 44.99 %RH |
  | `x1 / 4194304` | 44.99 %RH |
  | **`x1 / 1024` (v0.1)** | **184 291 %RH** |

  i.e. a factor of **4095.5 ≈ 4096**. v0.1 would have reported humidity four
  thousand times too large on real hardware, independently of issue #1.
* **Fix**: replace the hand-transcribed integer paths with the vendor's
  double-precision compensation from
  `BoschSensortec/BME280_SensorAPI` `bme280.c` (`compensate_temperature`,
  `compensate_pressure`, `compensate_humidity`), including their physical-range
  clamps. This removes the Q-format transcription risk entirely and is directly
  verifiable against upstream.
* **Validation**: the same numerical cross-check is kept as a regression test
  (`tests/test_bme280_math.py`) so that any future re-transcription of the
  integer form is caught.

### 2 — P0 — `CTRL_MEAS` writes forced mode while claiming normal mode, and nothing re-triggers a measurement

* **File**: `firmware/main/sensor.c:212-215, 220-249`
* **Root cause**: the comment says `mode=01 (normal)` but `0x01` in bits `[1:0]`
  is **forced** mode. In forced mode the chip performs exactly one conversion
  and returns to sleep. `sensor_read()` never writes `CTRL_MEAS` again, so every
  read after the first returns the same stale registers. Additionally the
  `CONFIG` write `(4 << 5)` sets `t_sb = 100` while the comment claims `t_sb=0`.
* **Fix**: adopt **forced mode explicitly** (correct for a duty-cycled,
  low-power node): on every sample, write `CTRL_HUM` then `CTRL_MEAS` with
  `mode = 0b01`, poll `STATUS.measuring` (bit 3) with a bounded timeout derived
  from the oversampling settings, then burst-read `0xF7..0xFE`. Never leave the
  sensor converting while the MCU sleeps.
* **Validation**: `sensor_trigger_measurement()` + `sensor_wait_measurement()`
  with `CONFIG_AS_BME280_MEAS_TIMEOUT_MS`; documented in `docs/hardware.md` and
  README; build verification; runtime "not measured yet" statement for the real
  sensor.

### 3 — P0 — `require()` is not an ESP-IDF build-system command

* **File**: `firmware/main/CMakeLists.txt:25-26`
* **Root cause**: `require("mqtt")` / `require("wifi")` do not exist in ESP-IDF
  (they are not CMake commands, and no such module defines them). CMake fails
  while generating the build system, so the firmware has never been buildable.
* **Fix**: declare the real components through `idf_component_register(... REQUIRES ...)`.
* **Validation**: `idf.py set-target esp32s3 && idf.py build` must succeed; the
  exact command and result go into `docs/build_validation.md`.

### 4 — P0 — two conflicting dependency mechanisms

* **File**: `firmware/main/idf_component.yml`
* **Root cause**: the manifest declares a *managed* component `mqtt` (fetched
  from the component registry) while the source `#include "mqtt_client.h"` is
  the built-in `esp-mqtt`. Depending on two mechanisms at once is exactly the
  ambiguity the review asked to remove, and two different `mqtt` components
  cannot both provide `mqtt_client.h`.
* **Fix**: keep **one** mechanism — `REQUIRES` for the built-in components
  (`esp_wifi`, `esp_event`, `esp_netif`, `nvs_flash`, `mqtt`, `driver`) — and
  reduce `idf_component.yml` to the `idf` version constraint.
* **Validation**: build; `firmware/dependencies.lock` contains no `mqtt` entry.

### 5 — P0 — the change score is defined three different ways

* **Files**: `simulator/adaptive.py:179-193`, `simulator/events.py:64-68`,
  `firmware/main/change_detector.c:89-100`
* **Root cause**

  | run-time | ROC window | ROC reducer |
  |----------|-----------|-------------|
  | `adaptive.py` (live scheduler) | the whole `_hist` = **variety window (30 s)** | **mean** |
  | `events.py` (GT + detection) | variety window (30 s) | **max** |
  | `change_detector.c` (firmware) | `CD_ROC_WINDOW_S` = **10 s hardcoded** | **mean** |

  `roc_window_s: 10` in the YAML is read into `self.roc_window` and then never
  used by `adaptive.py`. The specification therefore does not exist, and the
  firmware's `10` is a literal in a header rather than a mirrored config value.
* **Fix**: publish `docs/change_score_spec.md` as the single normative
  definition (mean ROC over `roc_window_s`), then make all three run-times
  consume the same config values. Windows become runtime fields of
  `cd_config_t`.
* **Validation**: `scripts/check_config_parity.py` + a parity fixture that runs
  the same input sequence through the Python scheduler and a host-compiled copy
  of the C policy and compares state/interval/score/event/upload.

### 6 — P0 — the ground truth depends on AdaptiveSense

* **File**: `simulator/events.py:74-114` (`ground_truth_events`), used by
  `analysis/analyze.py` and `simulator/replay.py`.
* **Root cause**: the "ground truth" event mask is computed by `_channel_scores()`
  — the same EMA/STD/ROC scoring that AdaptiveSense uses — applied to the full
  rate signal. The generator knows exactly when it injected a change but never
  records it. Evaluation is therefore circular: a strategy is scored on whether
  it can reproduce the output of its own scoring function, and GT and detection
  share the same thresholds, so the comparison cannot falsify the policy.
* **Fix**: the dataset generator emits independent labels next to the raw
  signal (`dataset/raw/*.csv` + `dataset/labels/*_events.csv`), because it is the
  component that *defined* the injected intervals. The detector then consumes
  those labels read-only. AdaptiveSense never participates in producing them.
* **Validation**: label files are committed; `tests/test_events.py` asserts the
  detector does not import the generator's event definitions; a scenario-A label
  file with a header and no rows yields `N/A`, not `0 %`.

### 7 — P0 — event matching is channel-blind and many-to-many

* **File**: `simulator/metrics.py:46-72`, `simulator/events.py:117-118`
* **Root cause**: `event_overlap()` compares only times, even though `Event`
  carries a `channel`. `n_true_pos` counts each GT event that overlaps *any*
  detection, so one detection can satisfy several GT events; latency takes the
  earliest of *all* overlapping detections; and a detection that already matched
  GT #1 is excluded from the FP count even if it is a spurious extra detection.
* **Fix**: channel-aware **one-to-one** matching: iterate GT events in time
  order, and for each pick the best unmatched same-channel detection inside the
  configured onset/overlap tolerance; mark it used. Remaining GT = FN, remaining
  detections = FP.
* **Validation**: dedicated tests — same-channel match, cross-channel overlap
  must not match, one detection cannot match two GTs, one GT cannot absorb two
  detections, tolerance boundary, unmatched → FN/FP.

### 8 — P0 — metrics are aggregated with a plain mean over scenarios

* **File**: `analysis/analyze.py:123-130`
* **Root cause**

  ```python
  summary = df.groupby("strategy", sort=False).mean(numeric_only=True)
  ```

  `compute_metrics()` returns `event_detection_rate = 0.0` when
  `n_gt_events == 0` (metrics.py:56). Scenario A has no events, so it
  contributes a literal `0 %` to every strategy's average — this is the source
  of the "66.7 %" column in the README, not a detection property. Counts
  (`missed_events`, `false_positive_events`) and latencies are also averaged
  rather than summed/recomputed.
* **Fix**: per scenario, keep `N/A` when `n_gt_events == 0`; overall use
  **micro** aggregation — `sum(TP)/sum(GT)`, `sum(FN)`, `sum(FP)`, and latency
  recomputed over the pooled matched-event latency list. Write both a
  per-scenario table and a micro-aggregated overall table.
* **Validation**: statistics tests (zero-event scenario → N/A, micro aggregate
  arithmetic, pooled latency); regenerated CSVs.

### 9 — P0 — Wi-Fi is stopped before light sleep and never restarted

* **File**: `firmware/main/power_mgmt.c:52-63`
* **Root cause**: `power_sleep()` calls `esp_wifi_stop()` unconditionally and
  the wake path never calls `esp_wifi_start()`. After the first sleep the
  station is down, the MQTT client disconnects, `communication_ready()` returns
  `false`, and `communication_publish()` returns `-1` — which `main.c` ignores.
  The documented lifecycle (`boot→connect→sample→sleep→wake→publish`) cannot
  complete a second cycle.
* **Fix**: pick one explicit strategy and document it. Chosen: **light sleep
  keeps Wi-Fi alive** — `esp_wifi_set_ps(WIFI_PS_MIN_MODEM)` once at start-up,
  then `esp_light_sleep_start()`; the modem is handled by the driver, so no
  disconnect/reconnect is needed. Deep sleep is the only path that powers the
  radio down, and it reboots by definition.
* **Validation**: documented Wi-Fi lifecycle in `docs/power_management.md`; a
  code-level invariant test that `power_sleep()` contains no `esp_wifi_stop()`;
  publish counters exposed so a 5-cycle run is observable on hardware.

### 10 — P1 — a sudden large change cannot enter ALERT directly

* **File**: `simulator/adaptive.py:208-224`, `firmware/main/adaptive_scheduler.c:32-59`
* **Root cause**: in STABLE the only permitted transition is `STABLE → ACTIVE`,
  so a score of 50 (vs `active_threshold = 8`) is treated as "moderately
  active". ALERT is reached only at the *following* evaluation, i.e. after the
  ACTIVE interval has already elapsed.
* **Fix**: severity-ordered evaluation — `score >= active_high → ALERT`,
  `else if score >= stable_high → ACTIVE`, `else STABLE`, with the existing
  relative hysteresis applied only to the *downward* edges so oscillation is
  still suppressed but escalation is immediate.
* **Validation**: `test_sudden_large_change_enters_alert_directly` asserts
  `state == ALERT` on the very sample that observes the jump.

### 11 — P1 — the ACTIVE interval ladder slows the node down after a change

* **File**: `experiments/experiment_config.yaml:66`, `firmware/main/config.example.h:77`
* **Root cause**: `active: [60, 30, 15, 5]`. Entering ACTIVE returns `60` — the
  maximum interval — precisely when the node has just observed change. This is
  the opposite of change-aware behaviour, and it is visible in the committed
  results (AdaptiveSense latency 26 s in scenario B, identical to Fixed-60s).
* **Fix**: `stable: [20, 40, 60]` (monotonically longer), `active: [15, 10, 5]`
  (monotonically shorter), `alert: [5]` (minimum). Mirrored in the C config.
* **Validation**: regenerated results; `test_active_state_uses_shorter_intervals_than_stable`.

### 12 — P1 — Python and firmware compare different quantities for upload delta

* **File**: `firmware/main/adaptive_scheduler.c:110-118` vs `simulator/adaptive.py:304-313`
* **Root cause**: Python computes `abs(value - last_upload) / noise_floor` and
  compares with `delta_threshold`; the firmware computes the raw
  `fabsf(value - last_upload)` and compares with the same number. A single
  `delta_threshold = 2.0` therefore means "2 °C" for temperature and "2 lux" for
  light on-device, while in simulation it means "2 noise floors" per channel.
* **Fix**: `normalized_delta = |value − last_upload| / noise_floor`, with the
  per-channel noise floors passed into the scheduler config.
* **Validation**: parity test over a fixed value sequence; config parity check
  that the C noise floors equal the YAML ones.

### 13 — P1 — the first valid sample is never uploaded

* **File**: `simulator/adaptive.py:288-317`, `firmware/main/adaptive_scheduler.c:95-118`
* **Root cause**: every upload predicate is guarded by a "have I uploaded
  before" condition (`last_up is not None`, `self._last_upload is not None`,
  `s->has_uploaded`). On a long stable run the first report may be delayed for a
  whole interval ladder, and the node is silent from boot.
* **Fix**: explicit `first valid sample → upload = true` in both run-times.
* **Validation**: `test_first_sample_is_uploaded` in the scheduler tests and the
  parity fixture.

### 14 — P1 — a failed publish is indistinguishable from a decision not to upload

* **File**: `firmware/main/main.c:149-156`, `firmware/main/communication.c:120-140`
* **Root cause**: `communication_publish()` returns `-1` when MQTT is not
  connected, and `main.c` discards the return value. `dec.upload` is only
  *upload_requested*. Nothing counts or logs the loss, and the scheduler still
  records the sample as uploaded, resetting the heartbeat/delta baseline.
* **Fix**: separate `upload_requested` from `publish_success`; log a warning on
  failure; maintain `publish_ok` / `publish_fail` counters; only update the
  scheduler's "last upload" baseline on success.
* **Validation**: log fields and counters in `main.c`; documented in
  `docs/methodology.md`.

### 15 — P1 — the power config name does not describe the behaviour

* **Files**: `firmware/main/power_mgmt.c:52`, `firmware/main/config.example.h:96`
* **Root cause**: `#if CONFIG_AS_DEEP_SLEEP_ENABLE` guards a call to
  `esp_light_sleep_start()`. A reader (and the reviewer) reasonably concludes
  deep sleep is active; it is not.
* **Fix**: replace the boolean with an explicit mode selection
  (`CONFIG_AS_SLEEP_MODE_NONE` / `_LIGHT` / `_DEEP`), default `LIGHT`, and mark
  DEEP as experimental and not enabled by default (deep sleep reboots, so the
  scheduler state cannot survive without `RTC_DATA_ATTR` persistence, which this
  version deliberately does not implement).
* **Validation**: the selected mode is logged at boot; `docs/power_management.md`
  states which mode is default and what the others would require.

### 16 — P1 — the adaptive sample log writes every sample twice

* **File**: `analysis/analyze.py:44-67`
* **Root cause**: for `AdaptiveSense` the writer loops over `res.decisions`
  (which already contains one row per sample and all decision fields) and then
  loops over `res.samples`, so every timestamp appears twice — once with
  `state`/`score`, once without. The committed
  `results/sim/*/AdaptiveSense.csv` files have exactly this duplication.
* **Fix**: one row per sample. The decision fields are merged into the sampled
  row; the second loop is deleted.
* **Validation**: `test_sample_log_has_one_row_per_sample`.

### 17 — P1 — the match tolerance is hardcoded

* **File**: `simulator/events.py:117` (`tol_s: float = 5.0`), `metrics.py:48,68`
* **Root cause**: a value that changes the FP/FN counts is a default argument in
  the code rather than part of the experiment configuration.
* **Fix**: `evaluation.event_match_tolerance_s` in `experiment_config.yaml`,
  threaded through `compute_metrics()`.
* **Validation**: tolerance-boundary test; config parity check.

### 18 — P1 — detection latency definition and aggregation

* **File**: `simulator/metrics.py:63-75`
* **Root cause**: (a) latency is `first_detection_start − gt_start` and can in
  principle be negative for a detection that starts before the GT onset while
  still overlapping; (b) only mean and median are reported, no p95; (c) the
  per-scenario means are averaged by `analyze.py`, not recomputed over the
  pooled matched pairs.
* **Fix**: clamp at `max(0, …)` per the specification, report the sample count
  alongside, add p95 (marked as unstable when n is small), and aggregate over
  the pooled latency list.
* **Validation**: latency tests including a pre-onset detection clamping to 0.

### 19 — P1 — average sampling interval is computed from the count, not the times

* **File**: `simulator/metrics.py:78`
* **Root cause**: `duration_s / samples_taken` assumes perfectly uniform
  sampling. For an adaptive policy the true quantity is `mean(diff(timestamps))`,
  and N samples define only N−1 intervals.
* **Fix**: pass the actual sample timestamps and use `mean(diff(...))`; report
  `N/A` for a single sample.
* **Validation**: `test_average_sampling_interval_uses_real_diffs`.

### 20 — P1 — a physical unit (mJ) is attached to an invented constant

* **File**: `simulator/metrics.py:97`, `experiments/experiment_config.yaml:86-88`
* **Root cause**: `energy_proxy_mj = uploads × 1.0` with no current, voltage or
  duration model. Presenting it in mJ invites reading it as a measurement.
* **Fix**: rename to `upload_energy_proxy` (dimensionless units) and
  report `number_of_uploads` and `estimated_payload_bytes` as the primary
  quantities. Physical units are withheld until an INA219 / Joulescope /
  Power Profiler measurement exists.
* **Validation**: metric names in CSVs, README and docs contain no `mJ`.

### 21 — P1 — the benchmark is too small and only contains favourable cases

* **File**: `dataset/generate_dataset.py`
* **Root cause**: 3 scenarios, 4 labelled event windows, all of them sustained
  and amplitude-large. There is no scenario where a short event falls inside a
  long sampling interval, no high-noise stable scenario to stress false
  positives, and no slow-drift scenario.
* **Fix**: add scenarios D (repeated events), E (short event, expected to be
  missable), F (noisy stable, no true event), G (slow drift), targeting roughly
  20 labelled events overall, with labels emitted by the generator.
* **Validation**: label counts in `dataset/labels/`; README discusses the
  fundamental limit that no sampled observation policy can react before a change
  has been sampled.

### 22 — P1 — the scheduler tests cannot fail for the documented reason

* **File**: `tests/test_scheduler.py:59-67`
* **Root cause**: `assert d.interval_s <= min_interval or d.state != STABLE`
  passes if *either* half holds, so it cannot detect the ACTIVE-ladder bug it
  was written to guard. `test_hysteresis_prevents_rapid_oscillation` only asserts
  `len(set(states)) <= 2`.
* **Fix**: assert exact state and interval — `state == ALERT` and
  `interval_s == min_interval` immediately after a large change — plus the full
  required test list (initial upload, backoff, moderate change → ACTIVE, ALERT
  uses min interval, recovery through hysteresis, bounds, oscillation count).
* **Validation**: the new suite; each assertion verified to fail on the v0.1
  behaviour before the fix.

### 23 — P1 — YAML and C configuration can drift silently

* **Files**: `experiments/experiment_config.yaml`, `firmware/main/config.example.h`
* **Root cause**: the two files are kept in sync by hand; nothing detects a

* **Validation**: script exits non-zero on an injected mismatch; runs in CI.

### 25 — P2 — legacy I2C driver

### 26 — P2 — misleading window macro and hardcoded window sizes

* **File**: `firmware/main/change_detector.c:18`, `change_detector.h:26-28`
* **Root cause**: `SLOTS_FOR(window_s)` expands to `2 * CD_VARIETY_WINDOW_S + 2`
  regardless of its argument, and the windows are compile-time constants that
  are not the ones in the YAML.
* **Fix**: real per-window capacity computed from a `CD_MAX_SLOTS` bound with a
  `static_assert`, and both windows carried in `cd_config_t`.
* **Validation**: build-time assertion; config parity check.

### 27 — P2 — unchecked returns and unchecked array indexing

* **File**: `firmware/main/sensor.c:115, 251-255`
* **Root cause**: the second calibration `bme_read()` ignores its return value;
  `sensor_channel_name()` indexes a 4-element table with an unchecked enum.
* **Fix**: check the return, and bound-check the channel argument.
* **Validation**: reviewed code path; no out-of-range access remains.

### 28 — P2 — the ROC list double-counts the most recent interval

* **File**: `simulator/adaptive.py:186-191`
* **Root cause**: `roc_vals` is built as `[roc_inst] + [deltas from rows]`, but
  `rows` already ends with `(now, value)`, so the `(previous, current)` pair is
  included twice.
* **Fix**: derive every ROC term from the history exactly once.
* **Validation**: parity fixture; ROC unit test on a known ramp.

### 29 — P2 — plot labels and the trade-off chart

* **File**: `analysis/plots.py:59, 85, 118, 152`
* **Root cause**: `f"Scenario {s[-1].upper()}"` labels the "repeated" scenario as

* **Fix**: label with the scenario id/name; state the aggregation in the title
  and axis labels.
* **Validation**: regenerated figures.

### 30 — P2 — the README overstates what four synthetic events can show

* **File**: `README.md` ("Results", "Limitations"), `docs/experiment_protocol.md`
* **Root cause**: the summary table's detection-rate column is the artifact of
  issue #8; the text says "full event detection within the scenarios"; the
  protocol says "reproducing the results from the paper" although no paper
  exists; `docs/hardware.md` documents a BH1750 that the driver does not
  implement; "identical policy" is claimed for Python and C, which issue #5

  soften the claims ("Python and firmware implementations follow the same

* **Validation**: README statements checked against `results/` and the code.

### 31 — P2 — flash size does not match the documented reference board

* **File**: `firmware/sdkconfig.defaults:6`
* **Root cause**: the file selected `CONFIG_ESPTOOLPY_FLASHSIZE_4MB` while the
  reference platform documented in `docs/hardware.md` and the README is an
  ESP32-S3 N16R8 (16 MB flash, 8 MB octal PSRAM). A build configured for 4 MB
  produces an image that will not use the board it was written for.
* **Fix**: `CONFIG_ESPTOOLPY_FLASHSIZE_16MB=y`, matching the stated hardware. The
  build log confirms the change
  (`--flash_size 16MB` in the generated flash command).
* **Validation**: build output; `docs/build_validation.md`.

## Areas confirmed *not* to be defective

Recorded so the review is not read as a list of assumptions:

* The BME280 temperature and pressure compensation polynomials
  (`sensor.c:125-155`) match the datasheet integer equations, including the
  `int64_t` intermediates used to avoid overflow in the pressure path.
* The humidity compensation expression itself (`sensor.c:158-170`) follows the
  datasheet-appendix integer formula, including the `x1` clamp. Three separate
  things were wrong around it: its *inputs* (issue #1), its final Q-format
  conversion (issue #1b), and nothing else. Because the integer form is easy to
  get subtly wrong, the replacement uses the vendor's double-precision equations
  verbatim rather than a corrected transcription.
* The EMA update rule and the deviation-against-previous-baseline convention
  are the same in `adaptive.py` and `change_detector.c`, and the time-based
  `alpha = dt / (dt + tau)` form is used consistently.
* `compute_metrics()`'s `_rate()` helper and the reduction definitions are
  arithmetically correct; the aggregation in `analyze.py` is what is wrong.
* `firmware/CMakeLists.txt` (the project-level one) and `sdkconfig.defaults`
  are otherwise valid for an ESP32-S3 N16R8 target (the flash-size setting was
  wrong; see issue #31).
